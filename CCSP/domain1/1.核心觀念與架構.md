# 二、Domain 1 的核心定位

CCSP Domain 1 並非偏重深層技術實作，而是聚焦於：

- **雲端概念**
    
- **角色與責任**
    
- **服務模型與部署模型**
    
- **治理、可攜性、風險邊界**
    
- **雲端特性如何影響安全與營運**
    

簡化而言，Domain 1 的本質是：

> **先理解雲端是如何被定義、如何被分工、如何被治理，再進一步談安全控制。**

因此，這個 Domain 的題目常見特徵不是「哪個技術最強」，而是：

- 哪個角色應負責
    
- 哪個模型最適合
    
- 哪種雲端特性導致某種營運與安全影響
    
- 哪個選項最符合 shared responsibility 的邏輯

# 四、核心觀念整理

## A. 角色與責任：誰定義，誰執行，誰營運

### 1. Data Owner 是需求與期待的定義者

本次題目明確指出，對資料安全的要求，例如：

- encryption
    
- access controls
    
- retention policies
    

最終負責定義者是 **Data Owner**。

### 關鍵原則

- **Owner 定義需求**
    
- **Custodian 執行與維護**
    
- **Provider 提供平台或服務能力**
    
- **Broker / Partner 協助整合、治理或評估**
    

### 易錯點

常見混淆是把「負責操作的人」誤當成「負責定義要求的人」。

### 記憶方式

- **Owner = 決定要保護到什麼程度**
    
- **Custodian = 負責落地與操作**
    
- **Provider = 提供雲端服務能力**
    
- **Partner = 提供專業支援與評估**
    

---

## B. SaaS / PaaS / IaaS：責任邊界比功能更重要

### 1. SaaS 的關鍵優勢

題目明確強調：  
SaaS 相較於 PaaS、IaaS 的核心優勢之一是：

- **降低應用更新與維護負擔**
    

因為更多工作由供應商負責。

### 2. 選擇服務模型的最重要考量

本次題組中特別強調：

> 在 SaaS、PaaS、IaaS 之間做選擇時，**最關鍵的是 security responsibility 的分工**。

不是：

- 初始成本最低
    
- 基礎設施控制最多
    
- 內部 IT 技術能力最少
    

雖然這些都重要，但在 CCSP Domain 1 的考法中，**共享責任邊界**是最核心的判斷依據。

### 3. Patch management 的典型分布

本次題組對 patching responsibility 的考法非常標準：

- **SaaS**：供應商負責最多
    
- **PaaS**：雙方分擔
    
- **IaaS**：供應商負責基礎設施，客戶負責更多上層項目
    

### 記憶方式

- **SaaS：最少自管**
    
- **PaaS：中間分工**
    
- **IaaS：最多自管**
    

---

## C. 部署模型：不是看名字，而是看需求匹配

### 1. Hybrid Cloud 是最常見的現實型答案

本次題組多次呈現 Hybrid Cloud 的標準考法：

當題目同時出現以下需求時：

- 部分資料須高度控管
    
- 部分 workloads 可利用公有雲彈性
    
- 需要兼顧法規與營運敏捷
    

答案通常偏向 **Hybrid Cloud**。

### 2. Public Cloud 的典型優勢

若題目主軸是：

- rapid iteration
    
- continuous deployment
    
- scalability
    
- DevOps agility
    

答案通常偏向 **Public Cloud**。

### 3. Private Cloud 的典型優勢

若題目強調：

- maximum control
    
- customization
    
- strict governance
    
- potentially faster RTO for critical apps
    

則答案通常偏向 **Private Cloud**。

### 4. Community Cloud 容易被誤選

Community Cloud 常被誤認為適合：

- 資料主權
    
- 同產業管制要求
    
- 特定法域控管
    

但若題幹明確提到同時還要使用某些 public cloud services，則答案通常不是 Community Cloud，而是 **Hybrid Cloud**。

### 記憶方式

- **Public = 速度、規模、敏捷**
    
- **Private = 控制、客製、可預測**
    
- **Hybrid = 混合需求的標準解**
    
- **Community = 特定共同需求，不等於所有合規題都選它**
    

---

## D. 雲端框架與標準：名稱相近，功能不同

### 1. CSA CCM

CSA Cloud Controls Matrix 的核心用途是：

- 評估雲端安全態勢
    
- 做 control mapping
    
- 對照 ISO、PCI DSS、NIST 等標準
    

重點在於 **assessment-oriented control matrix**。

### 2. ISO/IEC 27017

ISO/IEC 27017 的核心用途是：

- 提供適用於 cloud computing 的資訊安全控制指引
    

重點在於 **cloud-specific guidance**。

### 3. FIPS 140-2 Level 2 vs Level 3

本次題組指出，從 Level 2 升到 Level 3 的關鍵躍升在於：

- 更強的 tamper resistance
    
- 更強的 unauthorized access protection
    

### 易錯點

這類題型常見錯誤是把：

- framework
    
- guidance
    
- certification
    
- baseline control set
    

混成同一類。

---

## E. Vendor Lock-in、Portability 與 Containerization

### 1. 避免 vendor lock-in 的核心思路

題目指出，最佳策略是：

- **cloud-agnostic architectures**
    
- **standard data formats**
    

這種考法非常典型。

### 不應優先選的方向

- provider-specific features
    
- proprietary-only services
    
- 過度綁定單一供應商能力
    

### 2. Containerization 的正確理解

題目反映的關鍵概念是：

- Containers **提升 portability**
    
- 也可能 **改善一致性與某些安全性**
    
- 但前提是 **configuration 要正確**
    

因此，容器化不是自動安全，也不是單純 portability 工具，而是：

> **可攜性與一致性的促進器，但安全性仍取決於 image、runtime、orchestration 與設定品質。**

### 記憶方式

- **Portability 靠標準化**
    
- **安全性靠正確設定**
    
- **避免 lock-in 靠去專屬化**
    

---

## F. 雲端特性對安全與架構的影響

### 1. Broad Network Access

本次題組中，broad network access 的影響點是：

- diverse client platforms
    
- endpoint variability
    
- troubleshooting complexity
    

也就是說，廣泛網路存取的影響不只是方便，而是會增加：

- 存取情境複雜度
    
- 平台差異
    
- 疑難排解困難度
    

### 2. Rapid Elasticity

Rapid elasticity 的核心影響在於：

- 應用程式需要更適合自動擴縮
    
- 架構要偏向 **stateless**
    
- 元件要偏向 **loosely coupled**
    

這是雲原生設計的重要基礎。

### 常見錯誤

不應把 rapid elasticity 理解成：

- 完全不需要 capacity planning
    
- 必須手動擴充
    
- 只是資源帳單問題
    

真正重點在 **architecture readiness for elastic scaling**。

### 3. Serverless 的抽象化問題

題目指出，serverless 最大的量化測量障礙之一是：

- **decreased visibility into infrastructure components**
    

這反映出一個常見考點：

> 抽象化提高便利性，但也降低傳統基礎設施層級指標的可見性。

---

## G. Governance、Accountability 與 Documentation

### 1. Audit Trails 才是 accountability 的證據

本次題組中，最能證明 accountability 的文件類型是：

- **system-wide audit trails**
    

廣受認可的證據不是：

- policy document
    
- playbook
    
- high-level process paper
    

因為 accountability 強調的是：

- 誰做了什麼
    
- 何時做
    
- 影響了什麼
    
- 是否可被追溯
    

### 2. Edge + Cloud 的治理重點

在 hybrid cloud-edge architecture 中，Cloud Administrator 最重要的責任不是單一技術點，而是：

- **enforcing consistent governance and compliance policies across environments**
    

這是 Domain 1 很典型的考法：  
當環境愈分散，真正困難的通常不是功能整合，而是 **治理一致性**。

### 3. Cloud Service Partner 的角色

在 multi-cloud 生態中，Cloud Service Partner 的主要價值通常是：

- 第三方評估
    
- specialized services
    
- multi-cloud security support
    
- assurance / integration support
    

而不是全面接管所有日常營運責任。

---

## H. SaaS 導入後，IT 部門職能轉型

本次題組中，SaaS adoption 對 IT department 的最大影響是：

- 由傳統基礎設施維護，轉向  
    **vendor management** 與 **service integration**
    

### 這是 Domain 1 非常重要的觀念

導入雲端不代表 IT 消失，而是角色轉型：

- 少做硬體與 OS 維運
    
- 多做治理、整合、合規、身份管理、供應商管理
    

### 關鍵理解

雲端並非「把所有安全責任丟給供應商」，而是將內部職能重心重新配置。

# 五、本次題組反映出的高頻盲點

## 盲點 1：把“操作責任”誤認成“定義責任”

典型例子：

- Custodian / Provider / Administrator 被誤當成決策責任者
    

### 修正原則

先問題目是在問：

- 誰定義需求
    
- 誰維護系統
    
- 誰提供平台
    
- 誰協助整合
    

---

## 盲點 2：服務模型題過度看功能，忽略 shared responsibility

常見錯法：

- 只看 control 多寡
    
- 只看成本
    
- 只看技術彈性
    

### 修正原則

凡是 SaaS / PaaS / IaaS 題型，先判斷：

- security responsibility 怎麼分
    
- patching 誰負責
    
- 哪一層由誰維護
    

---

## 盲點 3：部署模型題容易被“名稱直覺”誤導

例如：

- 看到資料主權就先選 Community Cloud
    
- 看到高控制就先選 Hybrid
    
- 看到 mixed requirement 卻沒有想到 Hybrid
    

### 修正原則

部署模型應以 **需求組合** 為判準，而非名稱印象。

---

## 盲點 4：治理題容易選技術答案，忽略一致性與可持續性

例如：

- edge-cloud integration 題，容易先想 synchronization 或 zero trust
    
- 但題目實際在考 governance consistency
    

### 修正原則

只要題目出現：

- large enterprise
    
- multi-cloud
    
- hybrid
    
- edge
    
- compliance
    
- distributed environment
    

就必須優先考慮：

- policy consistency
    
- governance
    
- compliance alignment
    
- administrative oversight
    

---

## 盲點 5：看見 portability 題就只想到技術移植，忽略架構策略

避免 vendor lock-in 的題目不只是容器或工具，而是：

- architecture neutrality
    
- standardization
    
- decoupling from provider-specific dependency
    

---

## 盲點 6：CIA triad 題目容易只抓到其中一個面向

本次有題目顯示：

- 只看到 high availability，就選 regional replication
    
- 但題目問的是整體 CIA
    

### 修正原則

若題目問 CIA triad，答案必須同時涵蓋：

- Confidentiality
    
- Integrity
    
- Availability
    

單一 Availability 控制通常不夠完整。

# 六、Domain 1 解題框架

建議將 Domain 1 題目拆成以下步驟判讀。

## 第一步：先辨識題型

題目是在問哪一類？

- 角色責任
    
- 服務模型
    
- 部署模型
    
- 標準與框架
    
- 雲端特性
    
- 治理與可攜性
    

---

## 第二步：辨識題目重點在“定義”還是“執行”

這一步非常重要。

例如：

- **Owner** 常是定義
    
- **Custodian** 常是執行
    
- **Provider** 常是提供能力
    
- **Partner** 常是輔助或整合
    

---

## 第三步：遇到 SaaS / PaaS / IaaS，先畫責任邊界

幾乎所有服務模型題都可以先問：

- 哪些層由供應商負責
    
- 哪些層由客戶負責
    
- 這題問的是哪一層
    

---

## 第四步：遇到 Public / Private / Hybrid / Community，先看需求混合程度

- 混合敏感與非敏感 workloads → 常偏 **Hybrid**
    
- 高度控制與客製 → 常偏 **Private**
    
- 高敏捷、高彈性、快速 DevOps → 常偏 **Public**
    
- 共享產業需求 → 才較可能是 **Community**
    

---

## 第五步：遇到治理題，優先找可持續、一致、跨環境的答案

不要先被單一技術吸走注意力。  
治理題通常更偏好：

- consistency
    
- policy alignment
    
- auditability
    
- governance enforcement

# 七、考場秒殺口訣

## 角色

- **Owner 定義，Custodian 執行。**
    
- **Provider 提供服務，不等於定義業務要求。**
    

## 服務模型

- **SaaS 最少自管，IaaS 最多自管。**
    
- **選服務模型，先看責任切線。**
    

## Patch 管理

- **SaaS provider 最多，PaaS 共享，IaaS customer 最多。**
    

## 部署模型

- **混合需求先想 Hybrid。**
    
- **最高控制先想 Private。**
    
- **最高敏捷先想 Public。**
    

## 治理

- **分散環境最怕政策不一致。**
    
- **可稽核、可治理、可持續，通常比單一技術答案更像正解。**
    

## Portability

- **避免 lock-in 靠 cloud-agnostic，不靠 provider-specific。**
    

## Rapid Elasticity

- **自動擴縮要靠 stateless + loosely coupled。**
    

## Accountability

- **Policy 是宣告，audit trail 才是證據。**

# 九、總結

本次 Domain 1 題組反映出的核心重點，可濃縮為以下結論：

> **Domain 1 的高分關鍵，不在於背誦技術細節，而在於穩定判斷“誰負責、哪個模型最適合、哪個雲端特性導致何種治理與安全影響”。**

若解題時能先從以下三個問題出發，正確率通常會顯著提升：

1. **題目是在問角色、模型，還是雲端特性？**
    
2. **題目是在問定義責任，還是執行責任？**
    
3. **題目要的是技術功能，還是治理與責任邊界？**
