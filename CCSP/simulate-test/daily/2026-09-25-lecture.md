### `2.4` Data discovery 與 dashboards

- Outline：`2.4 Implement data discovery`（structured／unstructured／semi-structured／data location）。
- 考試用語情境：dashboard 常被放在 data discovery「問題／風險」清單裡，焦點是**管理層看見被美化的指標 → 錯誤決策**，不是「對外公告欄＝disclosure」。
- 複習動作：對照教材 data discovery 問題清單（含 data quality、dashboards、hidden costs 等）；M001 仍標 **Disputed**，複習時保留異議、勿當成已結案。

### `2.2` Storage types：volume vs object

- Outline：`2.2` 列出 long-term、ephemeral、raw、object、volume 等。
- 教材慣用語（Error Analyst）：**volume ≈ 掛給 VM 的虛擬磁碟（block）**；**object ≈ 物件＋metadata、常經 API**。
- 實務直覺可能正確但仍會失分 → 用關鍵字對照表（raw／ephemeral／long-term／volume／block／object／file／LUN）對齊考試用語。M002 為 **Disputed**。

### `4.7` Federation：web of trust vs trusted third party

- Outline：`4.7` Federated identity、IdP。
- 兩個模型要分開畫：參與者各自是誰、信任邊怎麼連。
- TTP（hub-and-spoke）裡，第三方通常是 **IdP／broker**，不是 service provider；同時分清 **IdP** 與 **SP／relying party**。

### `4.5` Shadow APIs 與政策對齊

- 當題幹用成本、繞過率、生產力等限定詞指出「政策／流程本身不符業務」時，優先選處理**根本原因**的選項，而不是只強化強制執行。
- 保留風險意識：未審查 API 的存量風險可能仍未解（M004 異議）；答題時先對準題幹問的是什麼。

### `4.2` SDLC：使用者與 requirements

- 「使用者最關鍵」常落在 **Define／requirements（business requirements）**：決定做什麼；Test／beta 是驗證是否符合已定需求。
- Business requirements＝該組織／系統的功能、效能、安全需求，通常來自使用者與業務 stakeholder，不是一般市場智庫資料可完全取代。

### 補充：Domain Tutor 群組教學（2026-09-25 群組 `ccsp-preparation`）

- **`2.2` 答題關鍵字**：題目出現 file、hierarchy、metadata 就選 object；出現 attached drive、block 就選 volume。實務上 S3 這類 object storage 是扁平的 namespace，看起來像資料夾的只是 key 的前綴，所以你的直覺不算觀念錯，是考試用語不同。
- **`2.4` dashboard 的意思**：這題的 dashboard 是給管理層看的內部圖表，把 data discovery 結果整理成圖形供決策使用，不是對外公告欄。風險是底下的人為了讓數字好看而美化畫面，主管因此下錯決策。
- **`4.2` Define 可以只靠智庫或 open data 嗎**：外部資料只能說明市場大致狀況，說不出「這個組織、這個系統」需要什麼功能、效能與安全要求，這些只能從使用者和業務 stakeholder 取得。題目的 user involvement 要理解成廣義的業務需求提供者，不一定是逐一訪談終端使用者。需求一開始定錯，測試只會確認你做出一個錯的東西，而且越晚發現修正成本越高。
- **`4.7` 兩種 federation 的取捨**：web of trust 是成員彼此直接信任，每個組織同時是 IdP 和 SP，成員一多就難以擴充。trusted third party 是大家信任同一個第三方 IdP 或 broker，各組織只當 SP，擴充容易，但第三方成為單點依賴。
