# 1. Common Criteria：ISO、CCRA、Certification Scheme 到底誰是誰？

## 題目

> What is the organization that publishes and maintains the Common Criteria certification program for IT products?

LearnZapp：**ISO**

## 分類：`[Q]`

這題把 **標準出版者（standards publisher）** 與 **認證體系（certification scheme）** 混在一起。

### 正確模型

Common Criteria 的技術標準目前對應：

- **ISO/IEC 15408**：IT security evaluation criteria
- **ISO/IEC 18045**：Common Evaluation Methodology（CEM）

ISO/IEC 的確出版並維護這些國際標準。

但是：

> **ISO 並不是單獨運作全球 Common Criteria certification program、也不是直接替產品發 CC certificate。**

真正的 operational model：

```text
ISO/IEC
   │
   └── publishes ISO/IEC 15408 / 18045
             │
             ▼
Common Criteria / CCRA ecosystem
             │
     ┌───────┴────────┐
     ▼                ▼
National Scheme    Licensed Labs
     │
     ▼
Certificate
```

CCRA（Common Criteria Recognition Arrangement）負責國際互認架構；各國的 Certificate Authorizing Schemes / Certification Bodies 執行認證。

### 考場怎麼做？

如果 LearnZapp 選項只有：

- NIST
- ISO
- NATO
- UNESCO

而 wording 明顯在問 Common Criteria 的「標準來源」，**選 ISO**。

但不要背成：

> ❌ ISO = 全球 Common Criteria 發證機關

要背：

> **ISO/IEC = CC 標準；CCRA = 國際互認；National Scheme = 實際 certification。**

### 最短口訣

> **ISO 寫規格，CCRA 做互認，各國 scheme 發證。**

# 2. Data Controller：不是「誰產生資料」，而是誰決定 WHY + HOW

## 題目

> In regard to most privacy guidance, the data controller is ______.

LearnZapp 答案：

> The entity that collects or creates the privacy data

## 分類：`[T]`

四個選項中它是最佳答案，但 wording 不夠精確。

## 正式 mental model

Data Controller：

> **決定 personal data 處理目的（purposes）與方式（means）的實體。**

也就是：

```text
Controller = WHY + HOW
Processor  = DO it for Controller
Subject    = WHO the data is about
Regulator  = OVERSIGHT / enforcement
```

### 關鍵：資料「描述誰」≠「由誰產生」

例如醫療資料：

```text
Patient = Data Subject

醫院可能建立：
- diagnosis
- lab result
- prescription
- billing code
- clinical risk score
```

這些資料是 **about patient**，但可能由醫院／醫師產生。

所以：

> **Personal Data 不必由 Data Subject 親自輸入或產生。**

### Controller 也不必親自 collect / create

例如：

```text
Company (Controller)
  │ 決定 purpose + means
  ▼
SaaS vendor (Processor)
  │ 實際 collect/store/process
  ▼
Personal data
```

Company 仍然是 Controller。

### 最短口訣

> **Subject = 誰；Controller = 為何＋怎麼；Processor = 代做。**

# 3. Cloud Provider 為什麼優先 Automating Service Enablement？

## 題目

Cloud provider 最應關注哪個 architecture trait？

LearnZapp：

> **Automating service enablement**

你選 MTTR。

## 分類：`[J]`

這題不是在說 MTTR 不重要，而是在問：

> **哪一個能力最像 cloud provider 的核心 operating model？**

### Provider 的核心經濟模型

Cloud provider 要處理：

- 大量 tenants
- 重複 provisioning
- elasticity
- self-service
- standardized deployment
- API-driven operations
- 低 marginal operational cost

所以：

```text
Automation
  ↓
Repeatability
  ↓
Scalability
  ↓
Lower manual cost
  ↓
Cloud operating model
```

MTTR / MTBF 是 reliability metrics，很重要，但不是 cloud provider 最具代表性的 architecture trait。

### 最短模型

> **Provider 題：先想 automation / scale / standardization。**

# 4. NIST SP 800-series 為什麼選 Price？這題要降權

## 題目

> Why might an organization choose to comply with NIST SP 800-series standards?

LearnZapp：

> Price

## 分類：`[Q]`

題庫想表達的是：

> NIST SP 800 publications 可以公開取得，因此「取得標準文件」成本低。

但：

```text
document acquisition cost
≠
implementation cost
≠
compliance cost
```

實際導入：

- controls
- tooling
- people
- assessment
- evidence
- continuous monitoring

都可能非常昂貴。

所以不要背：

> ❌ NIST 很便宜，所以 organization 選它。

正確 mental model：

> **NIST SP 800 是公開、成熟、廣泛引用的美國資安 guidance；文件本身容易取得，但 implementation 並不免費。**

另外，它不是「國際 acceptance」取向的 ISO framework。

### 考場看到 Price

若其他選項是：

- Ease of implementation
- International acceptance
- Speed

那 **Price 是 best available answer**。

但題目本身價值偏低。

# 5. ECC：為什麼 key 可以比較短？

## 題目

> This approach to public key cryptography uses much smaller keys than traditional cryptography to provide the same level of security.

答案：

> **Elliptical curve**（應理解為 Elliptic Curve Cryptography, ECC）

你選 AES。

## 分類：`[K]`

### 第一個快篩：public-key

題目已經明示：

> **public key cryptography**

因此 AES 可以先刪掉：

```text
AES = symmetric
ECC = asymmetric / public-key family
```

### ECC 的核心特色

相同大致 security strength 下：

> **ECC 通常比傳統 RSA / finite-field public-key schemes 需要更短的 key。**

簡化記：

```text
ECC 256-bit ≈ RSA 3072-bit
```

這不是說數值永遠一一固定，而是 security-strength 對比概念。

### 最短口訣

> **Public key + smaller key → ECC。**

### 不要混：

| 名稱 | 類型 |
|---|---|
| AES | 對稱式加密 |
| RSA | 非對稱式加密 |
| ECC | 非對稱／公鑰密碼學 |
| MD5 | Hash，且已不適合安全用途 |
| SSL | 傳輸安全 protocol family，不是 crypto primitive |

# 6. DNSSEC + IPsec + TLS 為什麼題庫叫 Isolation？

## 題目

> In order to ensure proper ______ in a secure cloud network environment, consider the use of DNSSEC, IPsec, and TLS.

LearnZapp：

> **Isolation**

你選 Multitenancy。

## 分類：`[Q]`

這題最值得保留的是：

> **不要讓題庫把 encryption / secure communications 和 isolation 混成同義詞。**

## Isolation 的精確模型

> **Isolation = security boundary + controlled information flow**

典型工具：

- VPC / VNet
- VLAN
- subnet
- firewall
- security group / NACL
- VRF
- namespace
- hypervisor tenant isolation
- physical separation
- VPN / encrypted logical separation（特定情境）

### Isolation 不等於「不能接 Internet」

```text
Internet
   ↓
WAF / FW
   ↓
DMZ
   ↓
App subnet
   ↓
DB subnet
```

這仍然是一個具有 isolation / segmentation 的架構。

所以：

> **Internet-facing ≠ not isolated**

---

## DNSSEC / IPsec / TLS 真正各自做什麼？

| 技術 | 最短功能 | Isolation？ |
|---|---|---|
| DNSSEC | DNS authenticity + integrity | ❌ 本身不是 |
| IPsec | L3 confidentiality/integrity/authentication；可做 VPN | ⚠️ 可支援 logical isolation |
| TLS | secure transport channel | ❌ 本身不是 segmentation |

因此這個組合更自然描述：

> **secure communications / protected communications**

而不是單純 isolation。

### 最短口訣

> **Isolation 看 boundary；TLS/IPsec 看 channel；DNSSEC 看 DNS integrity/authenticity。**

# 7. 今日 D1 Fresh 必用操題模型

你今天特別要保留這組。

## 7.1 `all / always / every service model`

看到：

> all cloud models  
> always  
> every service model

不要先找 AWS / Cloudflare / GCP 的反例。

先算：

```text
IaaS ∩ PaaS ∩ SaaS
```

也就是：

> **哪個能力在三種 service model 的交集中仍然成立？**

這是 ISC2 題型的集合題。

---

## 7.2 `most / best`

不是問：

> 哪個「也有幫助」？

而是：

> **哪個最直接回答題幹的 stated objective？**

快篩：

```text
Direct control
> enabling condition
> supporting capability
> downstream consequence
```

---

## 7.3 Provider / Customer Role

看到 CSP / CSC：

先問：

```text
Who owns?
Who operates?
Who configures?
Who remains accountable?
Who controls the layer mentioned?
```

尤其 service model 題：

```text
SaaS → customer control 最少
PaaS → app/data 較多
IaaS → OS/network config 等較多
```

但 shared responsibility 不是固定一張表；仍要看 service / contract。

---

## 7.4 Federation Role

先判斷：

```text
IdP = authenticate + issue assertion
SP/RP = consume assertion
Broker = 中介 federation / trust relationship
```

看到 centralized broker federation：

> **Broker 可能扮演 identity intermediary / IdP-like role。**

---

## 7.5 Abstraction Level

ISC2 很常故意把「上層概念」與「下層實作」放一起。

例如：

```text
Security
 ├─ Confidentiality
 ├─ Integrity
 └─ Availability
```

所以題目若問具體 property：

> 不要因為 `security` 比較大就選 security。

同理：

```text
Risk management
 ├─ identify
 ├─ assess
 ├─ treat
 └─ monitor
```

問特定 stage 就選特定 stage。

# 12. 今日狀態判定

今天不是單純的「知識量不足」。

真正暴露的是兩種問題：

1. **術語 precision**
   - Controller
   - Isolation
   - provider architecture role

2. **題庫 wording contamination**
   - Common Criteria = ISO certification program
   - DNSSEC/IPsec/TLS = isolation
   - NIST SP 800 = price

因此今天最重要的 remediation 不是多刷 30 題，而是把：

```text
Question wording
        ↓
Concept category
        ↓
Correct model
        ↓
Best available answer
```

這條路徑固定下來。
