


## 一、 Redis Success Program 概述

Redis Success Program 是一個旨在提供速度、簡單性與成功保障的計畫，幫助客戶從第一天起就建立高效率的團隊。

### 1. 核心支援團隊成員

- **客戶成功工程師 (Customer Success Engineer, CSE)：** 引領完成上線（Onboarding）、疑難排解並分享最佳實踐。
- **24/7 支援服務 (Support Services)：** 安全網，處理緊急突發問題。
- **技術客戶經理 (Technical Account Manager, TAM)：** 針對大型帳戶，提供主動式的架構審核、效能調校與擴展規劃。
- **客戶成功經理 (Customer Success Manager, CSM)：** 專注於業務對齊，確保 Redis 環境符合業務藍圖並展現投資價值。

### 2. 專業服務 (Professional Services)

對於更複雜的需求，Redis 提供專業服務，包括：**架構審核、遷移協助、效能優化以及客製化培訓**。

## 二、 生產就緒檢查清單 (Production Readiness Checklist)

這是確保系統在正式上線前已達到生產標準的藍圖，涵蓋以下六大類別：

|類別|準備就緒標準|
|:--|:--|
|**安全性 (Security)**|具備安全認證、加密通訊（TLS）、網路隔離、靜態加密與中心化稽核日誌。|
|**可觀測性 (Observability)**|配置監控與告警、日誌中心化、具備清晰的可視化儀表板（如 Grafana）。|
|**架構 (Architecture)**|環境配置正確、具備高可用性（HA）拓撲、持久化設置完成並已規劃容量。|
|**效能 (Performance)**|完成基準測試與壓力測試、配置已優化、延遲極小化並有明確的擴展策略。|
|**高可用性 (High Availability)**|測試過複製與容錯移轉、備份自動化且已驗證、完成多可用區（Multi-AZ）部署。|
|**客戶端整合 (Client Integration)**|正確配置連接池、實施重試邏輯、定義錯誤處理、啟用客戶端快取。|

## 三、 技術實作與操作要點

### 1. 安裝與升級

- **Ubuntu 衝突預警：** 在 Ubuntu 上安裝時，必須禁用或重新配置 `systemd-resolved`，因為它與 Redis Enterprise 同樣使用 **53 端口**。
- **滾動升級 (Rolling Upgrade)：** 生產環境應採用滾動升級，一次更新一個節點，以確保**零停機時間**。

### 2. 安全基礎設施

- **RBAC 與 ACL：** 使用基於角色的存取控制 (RBAC) 來管理使用者權限。
- **網路安全：** 應將 Redis 部署在受信任的網路中，限制防火牆存取，並建議使用 **VPC Peering** 進行私密連線。

### 3. 可觀測性框架 (RED Framework)

運維時應專注於 **RED** 指標：

- **Requests (請求)：** 追蹤流量、操作量與快取命中率。
- **Errors (錯誤)：** 監控失敗指令、連線逾時與逐出（Eviction）率。
- **Duration (持續時間)：** 測量 P50、P95 與 P99 延遲。

安裝、升級與基礎設施管理

1. 安裝注意事項

- **Ubuntu 端口衝突：** 在 Ubuntu 安裝時，必須禁用 `systemd-resolved` 或更改其端口，因為它預設佔用 **53 端口**，這會與 Redis Enterprise 的 DNS 服務衝突。
- **安裝腳本：** 使用 `install.sh` 進行安裝，並可搭配 `-y` 參數自動接受提示以利自動化腳本執行。
- **環境需求：** 需確認內核參數（Kernel parameters）、檔案描述符限制（File descriptors）與磁碟空間符合標準。

2. 升級策略 (Zero Downtime)

- **滾動升級 (Rolling Upgrade)：** 生產環境的標準做法。一次僅更新一個節點，並在處理下一個節點前驗證當前節點與分片的健康狀態。
- **方法選擇：**
    - **Replace Node Method：** 暫時移除一個節點，升級後再重新加入。
    - **Extra Node Method：** 加入帶有新版本的新節點，然後移除舊節點（需額外資源）。

三、 生產就緒檢查清單 (The Six Categories)

在正式上線前，必須通過以下六大面向的驗證：

|分類|關鍵實作要點|
|---|---|
|**安全性 (Security)**|實施 RBAC/ACL 存取控制、啟用 TLS 加密（傳輸中）與靜態加密（存儲中）、集中式審核日誌。|
|**可觀測性 (Observability)**|配置監控與告警、日誌中心化、建立可視化儀表板（如 Grafana 搭配 Prometheus）。|
|**架構 (Architecture)**|配置高可用性 (HA) 拓撲、設置持久化、規劃容量並激活必要模組。|
|**效能 (Performance)**|完成基準測試 (Baseline) 與壓力測試、優化配置、最小化延遲並制定擴展策略。|
|**高可用性 (HA)**|測試複製與容錯移轉、備份自動化且經驗證、完成多可用區 (Multi-AZ) 部署。|
|**客戶端整合 (Client Integration)**|正確設置連接池 (Connection Pooling)、重試邏輯、錯誤處理、啟用客戶端快取。|

四、 開發者最佳實務與技術細節

1. 數據建模選擇

- **Hashes：** 存儲平坦對象（Flat Objects）時比 Strings 更節省記憶體。
- **JSON：** 若數據具有深層嵌套結構，應選用 RedisJSON 以支援原子化局部更新。
- **Sorted Sets：** 適用於排行榜或需要依分數進行範圍查詢的場景。
- **HyperLogLog：** 處理海量數據的唯一計數（如不重複訪客數）時極度節省空間，標準誤差約 0.81%。

2. 避免開發反模式 (Anti-patterns)

- **禁用** **KEYS****：** 此指令會阻塞 Redis 服務，請改用 `SCAN` 進行增量掃描。
- **管理大鍵 (Big Keys)：** 避免單一鍵過大（如超過 1GB），這會導致延遲。應將大鍵拆分為多個小鍵。
- **熱鍵處理 (Hot Keys)：** 識別並透過分片或客戶端快取來分散熱點負載。
- **使用 TTL (Time To Live)：** 為快取數據設置過期時間，避免記憶體耗盡。

--------------------------------------------------------------------------------

五、 運維操作與故障排除

1. 核心管理工具

- **rladmin****：** Redis Enterprise 的主要命令行工具，用於查看狀態 (`rladmin status extra all`) 或手動觸發分片遷移 (`rladmin failover shard`)。
- **支援包 (Support Package)：** 當遇到問題時，運行 `log_collector` 工具或透過 UI 生成包含日誌、配置與統計數據的壓縮包供專家診斷。

2. 可觀測性：RED 框架

監控應專注於三個核心指標：

- **Requests (請求)：** 吞吐量、指令分佈與快取命中率。
- **Errors (錯誤)：** 失敗指令、超時與逐出 (Eviction) 次數。
- **Duration (持續時間)：** 關注 P50、P95 與 P99 延遲。

3. 持久化與災害恢復 (DR)

- **持久化模式：** **Hybrid (混合) 模式** 是推薦的預設設定，結合了 RDB 的快速啟動與 AOF 的數據完整性。
- **備份與還原：** 備份應存儲於遠端（如 S3 或 GCS）。**「複製 (Replication)」不等於災害恢復**，因為人為刪除或數據損壞會被同步，必須定期測試還原流程。
- **高可用性要求：** 必須部署奇數個節點（至少 3 個）與奇數個可用區，以維持法定人數 (Quorum)。

--------------------------------------------------------------------------------

六、 執行工作流：完成就緒評估

完成 Production Readiness Checklist 的標準流程為：

1. **學習 (Learn)：** 理解各項要求的背景。
2. **脈絡化 (Contextualize)：** 將要求映射到具體的集群與組件。
3. **負責 (Own)：** 指派明確負責人。
4. **實作 (Implement)：** 使用程式碼 (IaC) 配置並測試。
5. **提供證據 (Evidence)：** 檢附架構圖、測試日誌或儀表板截圖。
6. **評分 (Score)：** 從 A (自動化/已測試) 到 D (高風險)。**安全性與 HA 的缺口通常被視為上線阻礙因素 (Blockers)**。

## 四、 開發者最佳實踐與反模式

### 1. 數據結構選擇

選擇正確的類型能顯著提升效能與記憶體效率：

- **Hashes：** 儲存結構化物件比 Strings 更省空間。
- **Sorted Sets：** 適用於排行榜與範圍查詢。
- **HyperLogLog：** 用於極低記憶體消耗的大數據量基數計數（近似值）。

### 2. 避免開發反模式 (Anti-patterns)

- **禁用 `KEYS` 指令：** 此指令會阻塞 Redis，生產環境請改用 `SCAN`。
- **處理大鍵 (Big Keys)：** 超過 25,000 OPS 或單一分片 25GB 可能導致效能下降。
- **熱鍵 (Hot Keys)：** 應透過分片或客戶端快取來分散負載。

---

## 五、 災難恢復 (DR) 與持久化策略

**複製 (Replication) 並不等於災難恢復**，因為錯誤操作（如刪除數據）也會同步到副本。

- **持久化模式：** 推薦使用 **Hybrid (混合) 模式**，結合了 RDB 的快速啟動與 AOF 的數據安全性。
- **備份驗證：** 必須定期在非生產環境測試**還原流程**，確保備份文件有效。

---

## 六、 執行工作流：如何完成檢查清單

完成 Production Readiness Checklist 是一個循環過程：

1. **學習 (Learn)：** 閱讀要求並理解其架構背景。
2. **脈絡化 (Contextualize)：** 將項目映射到實際環境（如哪些 Cluster 受影響）。
3. **負責 (Own)：** 指派明確的負責人與截止日期。
4. **實作 (Implement)：** 使用程式碼 (IaC) 或腳本進行配置並測試。
5. **提供證據 (Evidence)：** 附上架構圖、測試日誌或監控截圖。
6. **評分 (Score)：** 分為 **A (完全自動化/已測試)** 到 **D (高風險/缺失)**。**安全性與高可用性的缺失通常被視為阻礙上線的因素 (Blockers)**。
